JWT & Signing Keys Guide

An interactive manual detailing how JSON Web Tokens work, symmetric vs asymmetric keys, verification flows, and local setup using Supabase's modern JWT Signing Keys.

What is a JSON Web Token?

A JSON Web Token (JWT) is an open standard (RFC 7519) that securely transmits user details as a signed JSON object.

Historically, backend applications verified JWTs by sharing a single Symmetric Secret Key (e.g. HS256) with the auth server. However, modern authentication servers like Supabase have migrated to Asymmetric Signing Keys (e.g. RS256/ES256).

Symmetric (Legacy) vs. Asymmetric (Modern)
  • Symmetric (HS256): A single secret key is shared between Supabase and your FastAPI backend. The same key is used to sign and to verify tokens. If the backend is compromised and the key is leaked, attackers can forge custom valid JWTs.
  • Asymmetric (RS256 / ES256): Supabase keeps a Private Key secret to sign tokens. It publishes a public key list called a JWKS (JSON Web Key Set) at a well-known endpoint: https://<project>.supabase.co/auth/v1/.well-known/jwks.json. Your FastAPI backend retrieves this public key dynamically to verify signatures. The backend can verify tokens but *never* has the capacity to sign/forge them.
Seamless Rotation: With asymmetric keys, Supabase can rotate keys without breaking your API backend. The backend dynamically fetches the new public keys from the JWKS endpoint, avoiding service disruption and manual environment variable updates.

          Setting up JWT signing validation in FastAPI
        

        
        
Since Supabase uses asymmetric signing keys by default for modern projects, you can verify tokens locally using **JWKS** (automatically querying and caching Supabase public keys). Let's review both configurations.

        
        

          
          
        


        
        

          
Step 1: Configure .env Variables

          
Add your Supabase JWKS endpoint URL in your .env file. This endpoint publishes your project's active public keys:

          

            
            
# .env
SUPABASE_JWKS_URL="https://your-project-ref.supabase.co/auth/v1/.well-known/jwks.json"

          


          
Step 2: Update FastAPI Dependencies

          
Update src/api/deps.py to retrieve keys dynamically using PyJWT's built-in PyJWKClient. This verifies token authenticity without needing any local secret key:

          
          
import jwt
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from src.config import settings

security = HTTPBearer()

# Initialize JWK Client with cache enabled
jwks_client = PyJWKClient(settings.SUPABASE_JWKS_URL)

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
) -> User:
    token = credentials.credentials
    try:
        # Get the verification key dynamically using the 'kid' claim in token header
        signing_key = jwks_client.get_signing_key_from_jwt(token)
        
        # Verify signature locally against public key
        payload = jwt.decode(
            token,
            signing_key.key,
            algorithms=["RS256"],
            options={"verify_aud": False},
        )
    except jwt.PyJWTError as e:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail=f"Could not validate credentials: {str(e)}",
            headers={"WWW-Authenticate": "Bearer"},
        )

    user_id = payload.get("sub")
    ...

Step 2: Verification dependency (HS256)

          
FastAPI decodes tokens using local HMAC-SHA256 signature checks:

          
import jwt
from src.config import settings

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
) -> User:
    token = credentials.credentials
    try:
        payload = jwt.decode(
            token,
            settings.SUPABASE_JWT_SECRET,
            algorithms=["HS256"],
            options={"verify_aud": False},
        )
    except jwt.PyJWTError as e:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail=f"Invalid signature or secret: {str(e)}",
        )
    user_id = payload.get("sub")
    ...


        

      

    


    
    

      

        

          

            
            Key Rotation Best Practices
          

          

            When utilizing **Asymmetric Keys (JWKS)**, you gain the ability to rotate credentials gracefully. Supabase handles rotation by introducing a new signing key alongside older keys during transition phases.
          

          
          
1. Cache TTL & Refresh

          

            PyJWT's PyJWKClient caches retrieved keys to avoid calling Supabase on every single API request. However, it will refresh the JWK list automatically if it encounters an unknown Key ID (kid) to check if a key rotation has just occurred.
          


          
2. Invalidation Window

          

            After rotating keys in the Supabase Dashboard under **Project Settings → JWT**, wait for existing client sessions to expire (or keep the secondary key active for a temporary window) before officially **revoking** the previous keys to avoid terminating logged-in users.
          


          

            

              Secure Backend: If your API backend environment variables are leaked, attackers **cannot** compromise your user base since they do not possess the private key required to forge valid session tokens.
            

          

        


        

          

            
            Validation Configuration
          

          

            FastAPI token verification should validate basic assertions to avoid exploitation:
          


          
1. Algorithm Restriction

          

            Always restrict accepted decoding algorithms explicitly:
            
algorithms=["RS256"]

            Failing to do so allows attackers to change the header to `HS256` and sign the token using the public key as a symmetric key (known as the *Algorithm Confusion Attack*).
          


          
2. Expired Claim checks

          

            Ensure your decoder enforces exp validation. PyJWT handles this automatically, throwing a ExpiredSignatureError if the token lifetime is exceeded.
          


          
3. Audience Bypass for Supabase

          

            Supabase uses customizable user claims and metadata in the audience (aud) payload field (often setting it to authenticated). To bypass default PyJWT checks looking for specific client audience IDs, configure:
            
options={"verify_aud": False}
